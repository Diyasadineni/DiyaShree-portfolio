Case Study 01
Serverless Text-to-Speech Converter
Designing a seamless voice generation experience on top of AWS serverless infrastructure
Role Full-Stack Designer & Developer
Timeline May 2025
Tools Figma · React.js · AWS
1
Problem & Research

The problem

Developers and content creators frequently need to convert written content into audio — for accessibility, podcasts, and documentation. Existing tools either required costly subscriptions or exposed API keys on the client side, creating security vulnerabilities.

  • Interviewed 5 developers and 3 content creators about their current TTS workflow
  • Found that 6 out of 8 users had concerns about API key exposure in browser-based tools
  • Competitive analysis of ElevenLabs, Google TTS, and AWS Polly direct integrations
2
Define

Key insight

Users want a zero-friction, single-screen experience: paste text, click convert, download audio. Security and speed are non-negotiable. The UI must abstract away all cloud complexity.

How might we build a TTS tool that feels as simple as a notes app, yet runs on enterprise-grade serverless infrastructure?

3
Wireframes

Lo-fi sketches → mid-fi screens

Explored 3 layout directions. Settled on a single-column focused layout with a large text input, voice selector, and a persistent download panel.

Screen 1 — Input
Screen 2 — Processing
Screen 3 — Download
4
Final UI & Architecture

Design decisions

  • Single-page React app with minimal UI — textarea, voice dropdown, convert button, audio player
  • All AWS credentials kept server-side inside Lambda; frontend only calls API Gateway endpoints
  • Loading state with progress feedback so users know conversion is happening
  • Direct S3 pre-signed URL for download — no intermediate server needed

Outcome: Achieved a fully serverless pipeline with zero credential exposure. The UI was praised by peers for its clarity — conversion to download in under 3 clicks. Scalable to thousands of concurrent users at near-zero idle cost.

Case Study 02
Agentic Research Assistant
Designing a human-centred interface for AI-powered multi-source research
Role AI Engineer & Interface Designer
Timeline March 2026
Tools Figma · LangGraph · LLaMA 3.3
1
Problem & Research

The problem

Researchers and students spend hours switching between search engines, PDFs, and note-taking tools to synthesise information. Existing AI tools either only use web search or only use uploaded documents — never both simultaneously.

  • Conducted guerrilla research with 6 graduate students on their research workflow
  • Pain points: context switching, unreliable AI answers, inability to cite sources confidently
  • Analysed tools like Perplexity, ChatGPT, and NotebookLM to map feature gaps
2
Define

User persona

Priya, 24 — a postgraduate research student who needs to answer complex questions by combining her own notes/PDFs with current web information. She distrusts AI tools that don't show their sources.

How might we design an AI research assistant that transparently retrieves from multiple sources and lets users trust its answers?

3
Wireframes

Exploration & iteration

Iterated through chat-first, split-panel, and document-sidebar layouts. The split-panel with source attribution won — users could see where every answer came from.

Chat panel
Source panel
Upload & settings
4
Final UI & System Design

Design decisions

  • Hybrid retrieval: ChromaDB for uploaded docs + live web search — both shown as labelled sources
  • LangGraph agentic loop visualised as a subtle "thinking" indicator so users aren't left waiting blindly
  • Every answer includes source badges (web / document) for full transparency
  • LLM evaluation scores (relevance + faithfulness) surfaced optionally for power users

Outcome: The hybrid retrieval approach reduced irrelevant answers by surfacing context from both real-time web data and personal documents simultaneously. Evaluation pipeline confirmed high faithfulness scores, building user trust in AI-generated responses.
